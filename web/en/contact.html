02 — Form

Compose the message from the page

This site is static: it has no server that receives forms. The button composes the email with what you type and hands it to your own email client. Nothing is stored here.

If you use a publicable signature different from your legal name, give it here. Used only as a reply address within the message. The reason is written into the email subject to direct it to the right process. For corrections, include the URL, the passage, the primary evidence and the proposed change. Do not send passwords, tokens or sensitive data.

How the button works

On submit, the page builds a mailto: address with the name, email, reason and message encoded, and instructs your browser to open the email client with the draft already written. You review it and decide whether to send it.

If the client does not open —or the message is too long for a URL— use the link shown below or write directly to anubiscastillo@visitarealdelmonte.online. The direct address is always visible on this page.

No message composed yet.

Open a blank message in your email client

Accessibility and JavaScript

Automatic composition of the message requires JavaScript. With JavaScript disabled the text is not composed by itself: the fields remain usable with keyboard and screen reader, and the direct address stays in view in section 01, in this note and in the footer. No essential content depends on the script.

Nothing is stored

This site does not save the form's content on any server of its own: it is a static build with no database and no message queue. The text travels twice: once inside the mailto: address your browser handles, and again when your email client delivers it. From that point on it depends on the email transport you use.

If you prefer not to open your client, copy the address and write the message manually.

Open gap: responsible security disclosure

We do not yet publish a responsible-disclosure channel; it is a gap we must close. The repository's security policy states expressly that no dedicated security contact address exists, and that there is no response-time commitment until an operating contact with a defined service is established.

Until then: do not publish exploitation details, credentials, tokens, personal data or attack instructions in public issues. If the repository has GitHub's private vulnerability reporting enabled, use that channel; if not, write to the institutional email with the description, the affected file or path, the steps to reproduce and the potential impact.

Safe report: no secrets or live credentials, with personal data and production records removed, without testing systems you do not own or have permission to assess, and with a minimal reproducible proof rather than destructive tests.

04 — Data transparency

What this site collects and what it does not

A description of this page's actual behaviour, written from the code that serves it. If anything changes, this section must be updated the same day.

What this page does not do

  • It does not install cookies: the shared script and the form script do not write document.cookie.
  • It does not use local storage: there are no calls to localStorage or sessionStorage.
  • It does not load analytics, tracking pixels, third-party scripts or social buttons: the only additional resources are the shared style sheet, the shared script and the header mark.
  • It makes no background requests: no fetch, no XMLHttpRequest, no telemetry.
  • It does not store the form data: there is no form server, database or message queue in this build.
  • It creates no accounts and logs in: member registration and TRI identity are in preparation and are handled by email.

What does happen, and does not depend on this page

Your browser requests the HTML file and the page's resources from the hosting server, and in that request the headers the browser sends by default are transmitted. That server's access logs are determined by the hosting provider, which is not yet published as its own institutional domain: see the application dossier, domain section.

Privacy notice and terms

The privacy notice and terms-of-participation texts are not part of this build of the site: they live as platform documents, in draft and subject to legal review, and do not constitute a compliance certification. Request them by email and they are delivered as a document, with its version and date.

The platform's notice is incomplete until the name and address of the responsible party and the privacy channel are published. For that reason the record remains closed.

05 — Why this channel exists

A reachable contact is part of the identity

One of the things someone reviewing an institutional application does is try to reach the organisation. This page exists so that that check has a result.

A registry of research organisations checks that the entity exists, that it is named stably and that there is someone behind it. A responding institutional email, a seat with a geographic identifier and published governance rules cover the reachable part. What they do not cover is the eligibility decision: that belongs to ROR alone, and no one can anticipate it from this site.

The postal address is withheld deliberately. Publishing a street, a number or a postal code that is not confirmed would be exactly the kind of data a curator checks and that, if it does not add up, discredits the rest of the record. It will be published when it can be verified, together with the WHOIS record of the site's own domain and the address of the data controller.

What a reader of this page may conclude
  • That a documented mailbox and an identifiable seat exist.
  • That four fields —privacy mailbox, phone, postal address and security channel— are declared as outstanding.
  • That human review and a response time are not yet published as a service.
  • That nothing here certifies or guarantees a third party's decision.
